## RL Load Balancer — Technical Report

### 1. Overview
**Purpose**: Reinforcement-learning-based load balancer that learns to route incoming requests across multiple simulated servers to minimize response time, maximize throughput, and maintain fair utilization.

**Core components**:
- Environment and server simulation (`src/environment`)
- RL agents (`src/agents`)
- Training CLI (`src/main.py`) and demo (`demo.py`)
- FastAPI backend and dashboard frontend (`src/dashboard`)

Artifacts generated by training are stored under `data/` (models, results, plots).

### 2. Architecture
- **Environment**: `LoadBalancerEnv` provides a Gym-like interface with discrete actions over N servers, stochastic request arrivals, optional failures and traffic spikes, and returns a shaped reward plus metrics.
- **Server simulation**: `ServerSimulator` models CPU/memory utilization, queueing, failures, and request processing latency.
- **Agents**: DQN (PyTorch), tabular Q-Learning, and A2C. Agents select a server index each step.
- **API**: FastAPI backend exposes health, metrics, start/stop training, and baseline comparisons.
- **Dashboard**: Static HTML/JS frontend that queries the backend; WebSocket helpers exist for push updates.

Key files:
- `src/environment/load_balancer_env.py`
- `src/environment/server_simulator.py`
- `src/agents/dqn_agent.py`, `src/agents/q_learning_agent.py`, `src/agents/a2c_agent.py`
- `src/dashboard/backend/api.py`, `src/dashboard/backend/websocket.py`
- `src/main.py`, `start_dashboard.py`

See `requirements.txt` for pinned versions.

### 4. Implementation Details
- Training loop now supports `dqn` only for a lean, low-compute prototype.
- Non-blocking training in API: background task with shared `training_state` for live metrics.
- Direct script execution from project root via `sys.path` injection of `src/` in `start_dashboard.py`, `main.py`, and `demo.py`.
- Metrics tracked: average response time, throughput, fairness (Jain’s), server utilizations; per-episode history recorded for the dashboard.
- Traditional baselines (round robin, least connections, random) provided for comparison (approximate simulation).

### 5. Known Issues and Encoded Workarounds
- Import paths: scripts append `src` to `sys.path` to avoid packaging overhead.
- API responsiveness: training runs as an asyncio background task; REST remains responsive.
- WebSocket broadcasting helpers exist but are not mounted on a route yet; frontend likely polls REST.
- `ServerSimulator` keeps an `avg_response_time` placeholder; environment-level averages are authoritative.
- Environment uses a simplified `(obs, reward, done, info)` signature internally for simplicity.

### 7. How to Reproduce
1) Install dependencies:
```
pip install -r requirements.txt
```
2) Train (DQN-only, lightweight defaults):
```
python src/main.py --agent dqn --episodes 200 --servers 3 --requests 500 --arrival-rate 8.0
```
3) Start dashboard:
```
python start_dashboard.py
```
Open the printed `file://.../src/dashboard/frontend/index.html` in your browser.

### Academic Report Outline (Detailed)

#### 1. Introduction

##### 1.1 Overview
This project implements a reinforcement-learning-based load balancer that learns a routing policy for distributing web requests across multiple servers. It uses a Gym-like simulation of servers and traffic, enabling controlled experiments on response time, throughput, and fairness.

##### 1.2 Need of System
- Traditional heuristics (round robin, least connections) ignore dynamic server states and traffic bursts.
- Modern workloads exhibit volatility and nonlinear interactions; data-driven policies can adapt better.
- RL enables online adaptation to latency, utilization, and failures, targeting multi-objective optimization.

##### 1.3 Objective
- Minimize average response time while maximizing throughput.
- Maintain fair utilization across servers (Jain’s fairness index).
- Compare RL policies against traditional baselines under stochastic traffic and failures.

#### 2. Literature Review and Research Gap
- Classic load balancing: round robin, least connections, random—simple but myopic to instantaneous resources.
- ML/RL approaches: prior works show promise using Q-learning/DQN for datacenter scheduling and network routing.
- Gaps addressed here:
  - Unified simulation combining failures, queueing, and nonstationary arrivals for RL evaluation.
  - Side-by-side instrumentation of response time, throughput, and fairness.
  - Pluggable agents (tabular Q, DQN, A2C) to compare value-based vs policy-gradient methods.

#### 3. Proposed System

##### 3.1 System Architecture / Block Diagram
- Components: Traffic generator → RL Agent → Action (server index) → Server Simulators → Metrics collector → Reward → Agent update.
- Data flow: The environment exposes state vectors (server stats + global metrics); the agent outputs an action; the environment applies queueing/processing, updates metrics, and emits reward and next state.

##### 3.2 Proposed Algorithm
- State: Concatenation of per-server metrics (CPU, memory, active/queued requests, normalized latency, status one-hot) and global metrics (normalized requests, failures, response time, progress, pending queue).
- Action: Discrete choice of server index.
- Reward: Positive for successful assignment, penalties for high utilization, long queues, and failed/overloaded servers; small bonus for balanced load.
- Agents:
  - Q-Learning: Tabular updates for small state abstractions.
  - DQN: Neural Q-function with replay buffer and target network (PyTorch).
  - A2C: Episode-based advantage updates (interface provided; learning at episode end).

##### 3.3 Results
- See “Training Results” above and `data/results/dqn_results.json` plus `data/results/plots/dqn_progress.html`.
- Example (DQN, 50 episodes): avg_response_time ≈ 32.03 ms, throughput ≈ 0.15 req/s, fairness = 1.0, failed_requests = 186.

#### 4. Experimental Setup

Dataset: Simulated traffic with exponential inter-arrival times, optional spikes (×3 arrival rate with p=0.1), and request sizes drawn from exponential/uniform/normal distributions. Servers can randomly fail with small probability; queues and processing model latency.

Results: Metrics collected each episode—reward, response time, throughput, fairness—and saved to JSON and Plotly HTML.

Repro: `pip install -r requirements.txt` then `python src/main.py --agent dqn --episodes 1000`.

#### 5. Scope
- Evaluate RL for intra-cluster request distribution under stochastic conditions.
- Extendable to new agents (PPO/SAC), advanced metrics, and real-time dashboards.
- Prototype scope; not production networking yet (simulation only).

#### 8. Conclusion and Future Scope
The RL approach achieves strong fairness and competitive response times in simulation. Future work includes: adopting PPO/SAC for stability and sample efficiency, wiring WebSocket pushes for real-time updates, improving baseline replay accuracy, and integrating persistence/monitoring for longitudinal studies. Transition to real traffic would require instrumentation, safety guards, and canary/A-B testing.
